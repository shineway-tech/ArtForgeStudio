# 积分中心与中秋充值加赠设计（待评审）

## 目标

将积分明细从充值页底部提升为独立的顶层 Tab，重新整理积分中心的信息层级，并在充值页内增加由服务端控制的中秋充值加赠展示。活动结束后，充值页自动回到普通状态，不需要再次发布客户端、重启服务或手工回滚配置。

本次活动采用中国时区，活动结束边界为半开区间：

```text
[活动开始时间, 2026-10-01 00:00:00 +08:00)
```

因此 2026 年 9 月 30 日 23:59:59.999（北京时间）前创建的订单可以获得赠送积分。

## 当前事实

- 当前充值页位于 `native-client/ui/pages/credits-page.slint`。
- 现有顶层 Tab 为充值、兑换码、订阅；积分明细位于充值页底部。
- `/v1/credits/packs` 返回服务端计算后的原价、会员折后价和基础积分。
- 充值订单只提交 `pack_code`，价格和权益由服务端重新计算并写入订单快照。
- 支付履约使用订单项快照，并已有订单与积分发放幂等保护。
- 当前充值档位为 1,000、5,000、10,000、30,000 积分，对应 ¥10、¥50、¥100、¥300。
- 会员折扣只影响实付金额；活动赠送只影响到账积分。

## 用户界面

### 页面外壳

保留当前软件的积分页外壳、标题、规则入口、白色面板、蓝紫色强调色和 `PillButton` 组件。不引入账号中心左侧导航，也不增加独立的“中秋活动”顶层 Tab。

顶部 Tab 固定为：

1. 充值
2. 积分明细
3. 兑换码
4. 订阅

### 充值 Tab

充值 Tab 的顺序为：

1. 当前积分余额卡，显示可用积分、冻结积分和充值记录入口。
2. 活动期间显示中秋活动 Hero；活动无效时整块隐藏。
3. 充值档位卡片。
4. 购买协议。
5. 底部充值确认栏。
6. 服务端目录说明。

中秋 Hero 使用深靛蓝月色背景、金色月亮、星点、灯笼和低密度玉兔线稿，文案由服务端返回，默认包括活动标题、活动说明和截止时间。Hero 只负责说明活动和提供规则入口，不复制完整的充值操作。

充值档位卡显示基础积分、赠送积分、总到账积分、会员折扣和当前账号的最终应付金额。卡片不放“选择”按钮；整张卡可点击，选中状态使用边框、单选标记和浅色底区分。页面只保留一个主操作按钮“立即充值”。

活动期间的推荐展示：

| 基础积分 | 赠送积分 | 到账总额 |
| ---: | ---: | ---: |
| 1,000 | 100 | 1,100 |
| 5,000 | 750 | 5,750 |
| 10,000 | 2,000 | 12,000 |
| 30,000 | 7,500 | 37,500 |

会员折扣继续由服务端计算。比如当前账号享受 8.5 折时，10,000 积分档应显示基础 10,000、赠送 2,000、到账 12,000、实付 ¥85；活动赠送不随价格折扣减少。

### 积分明细 Tab

将现有 `CreditLedgerSection` 移入独立 Tab，保留分页、加载、错误和空状态。顶部增加可用积分和冻结积分摘要，列表显示时间、类型、变动、余额和备注。中秋赠送记录使用服务端描述展示“中秋充值加赠”，不由客户端根据日期推断。

### 兑换码与订阅 Tab

保持现有交互和内容，只调整与顶部 Tab 的布局关系，不混入中秋活动文案。

## 服务端活动规则

新增版本化的活动数据模型，建议使用 `credit_promotions` 与 `credit_promotion_rules`：

- 活动：编号、版本、标题、副标题、开始时间、结束时间、状态、文案快照和配置摘要。
- 规则：活动编号、`pack_code`、赠送类型、赠送积分或比例、规则版本。

本次上线通过一次 migration/seed 写入中秋活动及四档规则。应用每次读取充值目录时按服务端当前时间判断活动是否在 `[start_at, end_at)` 内。活动结束后查询自然返回无活动状态，不依赖 cron、重启或后续手工配置。

`GET /v1/credits/packs` 在活动期间增加活动字段，至少包括：

- `bonus_credits`
- `total_credits`
- `promotion_id`
- `promotion_label`
- `promotion_ends_at`

活动失效后，`bonus_credits` 为 `0`，`total_credits` 等于基础积分，活动字段为空或明确返回 inactive。现有基础字段语义不变：`credits` 继续表示原始充值积分，`payable_price_cents` 继续表示会员折后价。

订单创建必须在服务端事务中重新评估会员折扣和活动规则，不能信任客户端传入的赠送值。订单项快照保存：

- pack/version
- 基础积分、赠送积分、总积分
- 活动编号/版本/时间窗
- 会员方案和折扣
- 原价、折扣额和最终应付金额

活动期间创建、活动结束后支付的订单仍按订单快照发放赠送积分。支付回调不重新计算活动。

履约初版将基础积分和赠送积分合并进现有充值 lot，metadata 中记录两者拆分、活动编号和订单编号，以保持当前团队账务校验和幂等链路不变。邀请返利默认只按基础积分计算，避免赠送积分放大返利成本；该口径需要在订单快照和返利测试中固定下来。

当前服务端没有通用充值退款/冲正流程。本活动沿用现有充值退款政策；如果业务要求回收已发放或已消费的赠送积分，必须先增加带审计的充值冲正流程，不能人工修改余额。

## 客户端数据与兼容

客户端增加可选的活动字段和总到账字段，所有金额与积分仍使用服务端字符串值，不在客户端计算或判断活动日期。旧客户端可以忽略新增字段，活动权益仍由服务端订单快照保障。

发票与历史充值识别不能继续只用当前档位的 `credits` 匹配 ledger 的总变动；需要优先使用订单快照或 ledger metadata 中的基础积分和原始价格，确保活动订单在活动结束后仍能正确识别。

活动字段为空时，客户端隐藏 Hero、赠送文案和活动说明，充值卡回到普通展示。进入积分页或刷新账号快照时重新读取服务端状态。

## 验证边界

- 开始前 1 毫秒不赠送，开始时赠送，结束前 1 毫秒赠送，结束时不赠送。
- 会员折扣与活动赠送同时生效，最终应付金额不因赠送改变。
- 活动订单在结束后支付、重复支付通知和履约重试仍只发放一次总积分。
- 活动结束后新订单恢复原价和基础积分，无需额外配置。
- 团队主账号的赠送积分进入当前付款账号组；无权限成员不能绕过 owner 限制充值。
- 邀请返利只按基础积分计算。
- 旧订单、旧客户端和历史活动订单的积分明细、发票识别和余额守恒保持正确。
- OpenAPI、服务端目录测试、订单快照测试、履约幂等测试、客户端 UI projection 测试和页面结构测试同步更新。

## 发布与回滚

首次上线需要一次客户端版本和服务端 migration/seed。服务端活动数据可以在发布时一次写入；结束后不需要再次发布或配置。若上线前需要关闭活动，只需将活动状态设为 inactive，基础充值目录仍可用。回滚 migration 时必须恢复活动记录和规则的版本完整性，不修改历史已创建订单快照。
